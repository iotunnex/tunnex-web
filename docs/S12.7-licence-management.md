# S12.7 — licence management. Commit-one.

⛔ **Founder-ruled: payments stay offline.** This story builds a structured way to ASK for a paid licence, a
way to SEE what has been issued, and a way to mint without a request. It builds no payment processing, no
card handling, and no automated issuance.

---

## The shape, stated before anything is built

> ## ⛔ **THERE IS NO DELETE, AND THERE IS NO UPDATE.**

Tunnex verifies licences **offline**. A deployment never calls home, so nothing this service does after a
key leaves can reach it.

|                   | consequence for this surface                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------- |
| **No revocation** | a key that left runs to its own expiry. A mistake is not corrected; it is OUTLIVED.                         |
| **No update**     | changing a band, a term or a domain means minting a **NEW** key. The old one stays alive alongside it.      |
| **No delete**     | the ledger is the only record of what is in the world. A row removed is a key we can no longer account for. |

⭐ **So three rules bind every screen in this story:**

1. **The surface must never imply otherwise.** No "edit", no "revoke", no "delete" — not greyed out, not
   hidden behind a confirm. A control that cannot work must not exist to be looked for.
2. **The ledger shows ALL of a customer's keys, never one replacing another.** A re-issue ADDS a row. A
   screen that showed "the current key" would be stating something false: the previous key is still valid
   until its own expiry, and the customer may still be running it.
3. **Re-issue shows the prior keys beside the new one**, so nobody can assume the old one stopped.

## Measured before designing

### What the tables carry

| table                  | columns                                                                                                    | read by                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `issued_keys`          | `license_id` UNIQUE · domain · band · kid · issued_at · expires_at · **licence_key** · emailed_at          | ⛔ **nothing.** One `LEFT JOIN` in the queue screen surfaces a single prior key per domain. |
| `licence_review_queue` | `trial_domain` **UNIQUE** · tier · issued_at · expires_at · license_id · queued_at · decided_at · decision | the pending queue only. Decided rows are written and never read again.                      |
| `trial_requests`       | email · domain · token_hash · expires_at · consumed_at                                                     | the magic-link verify. ⚠ **No band, no term, no kind** — it can only express "a trial".     |
| `trials`               | domain UNIQUE · email · status · license_id · clock                                                        | the duplicate-domain check                                                                  |
| `enterprise_leads`     | name · email · company · **seats** · message                                                               | ⛔ **nothing.** One INSERT + a notification email.                                          |

### ⛔ THREE FINDINGS THAT CHANGE WHAT CAN BE BUILT

**1. The one-per-domain rule does not refuse a returning customer. It silently discards them.**

`issuance.ts:176` inserts `ON CONFLICT (trial_domain) DO NOTHING` against `UNIQUE(trial_domain)`, and
decided rows are retained forever (deliberately — "a refusal we cannot explain later is worse than a row we
kept"). A company that took a trial and now wants to BUY hits a row that already exists, and their request
is dropped **with a success response**.

> ⚠ **This is not a refusal that needs softening — it is a no-op with no observer.** The customer is told
> it worked, and no row, log line or email says otherwise.

⭐ **The fix is a migration, not a message.** SQLite cannot drop a column-level UNIQUE, so `0004` rebuilds
the table and moves uniqueness to a **partial index over PENDING rows only**: one open request per domain
at a time, any number of settled ones over a customer's life. That is the rule the product actually wants —
"don't queue the same thing twice", never "you already had your turn".

**2. The paid path collects the wrong number and files it where nobody looks.**

`/enterprise` asks name, email, company, **seats** and a message. `2806b2e` replaced seat pricing with
per-gateway pricing two commits earlier. There is no email verification, no domain proof, no band and no
term — and `enterprise_leads` is read by nothing.

**3. The queue physically cannot hold a paid band.**

`trial-issuance.ts:37` hardcodes `tier: 'trial'` and is the queue's only producer. `BANDS` carries
`trial · starter · growth · scale`; **three of the four have never reached the signing surface.**

⭐ **What is already right, and stays untouched:** `issueFromQueue` builds `tier: row.tier === 'trial' ?
'trial' : 'enterprise'` with `band: row.tier`, so a paid band mints correctly the moment a row can carry
one. The signing path, the self-verify, the record-before-send ordering and the claim-then-act arbiter are
all unchanged by this story.

## What gets built

### 1. A paid request path

A form asking for a **paid band**: work email, company, the band they want, the term, and what the founder
needs in order to price it (gateway count, sites, anything else they want to say).

- **Same email verification, same domain proof as the trial** — the magic link, the derived eTLD+1, the
  same consumer/disposable refusals. A paid request from an unverified address is a stranger's typing.
- ⛔ **It lands in the SAME queue**, marked as a paid request. Two queues is two places to forget to look.
- ⛔ **The requester ASKS; the reviewer SETS the band that gets minted.** The asked-for band is recorded as
  what they asked for and is never the value that reaches the signing claims. **Nobody gets Scale by asking
  for it.**
- ⛔ **A paid row shows as PENDING PAYMENT and cannot be signed.** The founder settles money offline, and
  the first mistake available on this screen is signing before it arrives.

  > ⚠ **A trial mistake expires in 30 days. A paid key is a year and cannot be recalled.** The states are
  > `pending_payment → paid`, the transition is a deliberate act on the row, and Sign is unreachable until
  > it has happened.

### 2. The licence list — the read that does not exist

Every key ever issued: domain, band, term, kid, issued-at, expires-at, and whether it is **currently within
term**. Grouped by domain, so a customer's whole history is one block.

⭐ **Re-issue** mints a replacement **with the customer's prior keys shown beside it** — because the old key
did not stop, and the screen must not let anyone think it did.

### 3. Direct issuance

The founder closes a deal offline and mints against a domain and a band with no request existing.

⚠ **It goes through the SAME signing path**, by creating the row it would have had. One path from a decision
to a signature; a second minting site is a second place for the ordering rules (claim → mint → self-verify →
record → send) to drift.

### Everything behind Cloudflare Access, as the queue already is

⛔ **REGISTERED, AND IT GETS WORSE WITH EVERY SURFACE ADDED BEHIND IT:** `ADMIN_TOKEN` is one shared bearer
string with no identity, and it still travels in a URL on first use (`?t=` is exchanged for an HttpOnly
cookie, which fixed the history/Referer leak but not the shape). This story adds three more surfaces behind
it. Access is the control; the token is the floor — and the floor does not know who is standing on it.
